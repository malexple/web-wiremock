# План: интеграция скриптов wiremock-js в web-wiremock

## Фаза 1 — Каркас UI + реальные данные
- Backend: ExtensionAvailabilityService — разовая (кэшируемая) проверка наличия
  расширения wiremock-js, флаг прокидывается в navbar через ControllerAdvice.
- Backend: WiremockJsClient (Feign) — обёртка над Admin API расширения
  (GET/POST/PUT/DELETE /extensions/wiremock-js/scripts).
- Backend: подтвердить схему хранения scriptId (metadata vs transformerParameters,
  см. открытый вопрос выше) до реализации join-логики.
- Frontend: пункт меню "Scripts" в navbar, видимый по флагу.
- Frontend: scripts.html — layout filter-bar / список слева / detail-panel справа
  (переиспользуем стили tree-sidebar/detailPanel из stubs).
- Frontend: scripts.js — построение иерархии скрипт → стабы:
    - вариант А: N вызовов find-by-metadata (по одному на скрипт) + 1 вызов
      для осиротевших стабов;
    - вариант Б: 1 вызов getAllMappings + client-side join.
- Правила отображения дерева:
    - скрипт с 0 стабов — узел без разворота, бейдж "0" бледным;
    - скрипт с N стабов — бейдж N, дети — стабы;
    - осиротевшие стабы — отдельная группа внизу списка.
- Клик по скрипту → таб "Код скрипта" (read-only просмотр) + заглушка
  "Запуск скрипта" (не активна до Фазы 4).
- Клик по стабу → три таба: JSON, Код скрипта (редактируемый, с баннером
  "используется в N стабах"), Run Test (существующий функционал стаба).

## Фаза 2 — Создание и редактирование скрипта
- Модалка: Шаг 1 (имя, описание, seed-чекбокс + число).
- Конструктор логики (Salesforce-style):
    - Блок А — переменные (jsonField/query/header → var).
    - Блок Б — функции (now, uuid, randomInt, matches).
    - Блок В — одно if + опциональный else, "Тогда/Иначе" = status +
      плоские пары ключ-значение либо готовый JSON-текст.
    - Необратимый переход "Перейти в код" с предупреждением, дальше —
      обычный текстовый редактор с сохранением текущего кода.
- Cheat Sheet — сворачиваемая панель, доступна только в ручном режиме
  (и в read-only/edit просмотре кода в правой панели), вставка по курсору.
- Backend: CRUD скриптов через WiremockJsClient, счётчик символов на фронте
  под лимит MAX_SCRIPT_LENGTH.

## Фаза 3 — Создание стаба под скрипт + удаление скрипта
- Кнопка "+ Добавить стаб" на узле скрипта → урезанная модалка:
  имя, method, URL-тип+значение, JWT/clientId, priority/persistent
  (с разумными дефолтами). scriptId подставляется автоматически
  (в metadata и/или transformerParameters — см. вариант из открытого вопроса).
- Удаление скрипта с привязанными стабами — модалка с 3 действиями:
  Отмена / Отвязать стабы (очистить wiremock-js transformer + scriptId,
  стаб становится осиротевшим) / Удалить всё (последовательные DELETE
  стабов, затем DELETE скрипта).

## Фаза 4 — Тестирование скрипта (Run Test)
- Run Test на уровне стаба: тест через реальный вызов WireMock
  (существующий RunTestService), эффект виден в Request Journal.
- Финальный дизайн генерации тестовых данных — решаем по факту,
  после того как заработают Фазы 1–3.

## Фаза 5 — Оптимизация bulk-операций (после Фазы 4)
- Bulk-эндпоинт на бэкенде для массового удаления/отвязки стабов
  одним вызовом вместо цикла DELETE/PUT из браузера.
- Ревизия способа построения иерархии скрипт→стабы, если объём данных
  или число расширений вырастет.
